# Replay and investigation architecture

`src/normalize.ts` validates source envelopes, parses provider fields, derives a small normalized event, fingerprints the complete input record, rejects conflicting IDs, and removes exact duplicates. Unknown fields inside source records are tolerated for forward compatibility and are not persisted. Envelopes and normalized events are strict. The authenticated tenant is never accepted from event content.

`src/engine.ts` validates the rule DSL and groups events by the exact tuple `(provider, account, actor)`. Ordering uses parsed source time and then event ID for deterministic output. A sequence requires strictly increasing timestamps, so equal-time events do not imply causality. Windows include their endpoint. IDs, method names, outcome fields, role context, and account scopes remain visible in evidence through their normalized representation.

Match rules emit one finding per matching event. Sequence rules index matching candidates for each step and binary-search the earliest strictly later candidate. They emit at most one earliest-completion sequence per first event. They do not enumerate every combinatorial path or establish that a newly granted identity caused subsequent activity. The actor is the principal performing the API calls, not necessarily the target of a policy grant. Different starting grants can therefore produce overlapping findings. Candidate indexing keeps evaluation bounded rather than rescanning every suffix for every start.

Threshold rules slide over matching events, count unique normalized events, and emit when the threshold is met. They suppress another alert in that group until more than one full rule window after the last emitted end time. Findings hash rule ID/version and supporting event IDs/fingerprints. The overall replay also includes a digest of the full rules and normalized input. Change a rule's version when changing behavior; a findings-only ID is not a replacement for the full rules digest.

`src/replay.ts` composes normalization and detection and evaluates labeled scenarios. Metrics use one binary observation per scenario and rule, not per event or alert. Precision is TP/(TP+FP), recall is TP/(TP+FN), and false-positive rate is FP/(FP+TN). An undefined denominator yields null. Expected rule IDs must exist, scenario IDs must be unique, and rule IDs must be unique.

`src/app.ts` authenticates and authorizes replay, assigns the storage tenant from the server identity, validates the complete batch before writing, persists the normalized investigation, and records an audit event in one transaction. Any malformed event rejects the batch without a partial run. Reads and deletes include a tenant predicate. Analysts replay and inspect, operators can also delete, and agents cannot investigate.

Each run is self-contained. Persistence retains investigations, not a continuously updating correlation state. The 100-run tenant quota and 2,000-event batch bound favor inspectable experiments. The HTTP body limit may be reached before the event-count limit. No background ingestion, scheduling, watermark, distributed queue, alert notification, or remote deployment is implied.
